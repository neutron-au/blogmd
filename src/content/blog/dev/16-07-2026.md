I've been slacking a little bit this uni break. I was hoping to get the G4ED run stand going before starting my internship but it looks like that may not happen. I started looking into how I had architected certain parts of the firmware for my Theta3 ECU, and I wasn't happy with it.


### MetaConfig
In the very first iterations of the Theta firmware, progress was heavily limited by how slow adding configurable parameters were. Each time I wanted to add a parameter that could be edited in the tuning software, I would have to implement the variable in the firmware, update the serial handler/router to add support for that specific variable, add serial support for the variable in the tuning software (TS), and then add a custom widget dedicated for that variable, and tie it into the serial handler. Incredibly slow, very tedious, and most certainly would not have scaled to what it is today. 

I sought after a new and better way to handle config communication between Theta and TS. I sat down and actually had a good long think for once. Configs need to be as lean as possible, I shouldn't have to add custom serial communication for each individual config, nor each parameter that is inside each config. Configs and the parameters within then need to be self-discovering, and capable of storing simple fixed length types (e.g. float, int32, boolean, etc).

#### The Solution
MetaConfig is the base 'smart' config struct used in the firmware. It allows myself and potential future developers to create and group together configurable parameters used by various parts of the firmware, for example, each function. In this case, a function is a specialised part of the firmware that performs a specific *function*. A good example of this is the engine RPM limiter.

MetaConfig has an init function (required to be overridden by subclasses), as well as a vector of pointers to MetaConfigValues. Note that heap allocation is generally bad practice in engine management systems, but in our case the instantation of MetaConfigValues and adding a pointer to them in the std::vector is done during boot, long before the engine is even running.

<br>
```cpp
struct MetaConfig {
    uint16_t id;        // dynamic ID, assigned when added to config registry.
    std::string strid;  // string identifier for this config (must not be changed at all after used in published firmware).
    std::string path;   // path used if displayed in tuning software treeview.
    virtual void init(void) = 0;
    SerialClass entity {SerialClass::Unknown};  // entity that owns this config
    std::vector<MetaConfigValue*> fields;

    MetaConfigValue* getValue(uint16_t id) {
        for (MetaConfigValue* value : fields) {
            if (value->id == id) {
                return value;
            }
        }
        return nullptr;
    }
};
```
<br>
```cpp

struct MetaConfigValue {
    uint8_t     id;
    const char* name;
    const char* display_name;
    virtual SerialAttrType type() const = 0;
    virtual size_t get(uint8_t*       out,  size_t max) const = 0;
    virtual bool   set(const uint8_t* data, size_t len)       = 0;
    atomic32_t _raw;  // holds raw 32bit value
};
```

This format allows for safe, seamless creation of configs for various needs. Subclasses inherit from MetaConfig, define their own MetaConfigValue parameters (with specified type), and override the init method to add pointers of the new fields to the pointer array.

The pointer array is currently only used to allow the serial handler code to iterate over available parameters in a given config, e.g. when the TS sends a GetMeta command alongside the MetaConfig ID, the serial handler will retrieve the config from the ConfigRegistry, iterate over the available parameters, and send them back to the tuning software. No specific handlers for each config, or its parameters are required. The same code works for all configs.


#### Subclass Example
Below is an example of how a new MetaConfig subclass is created, and used to store parameters that are specific to a particular *function*.

```cpp
struct DevelopmentBlinkFunctionConfig : MetaConfig {
    ConfigValue<bool>     enabled      {0, "enabled",    "Enabled",        {true}};
    ConfigValue<float>    frequency    {1, "frequency",  "Frequency (hz)", {5.0f}};
    ConfigValue<float>    duration_ms  {2, "duration",   "Duration (ms)",  {1.0f}};
    void init(void) override {
        // set unique string id for this config
        strid = "dev_function_blink";  // do not change!
        path = "/Develop/Function/LED Blink Config";
        g_metaconfig_registry.registerItem(this);
        // add values to array
        fields.push_back(&enabled);
        fields.push_back(&frequency);
        fields.push_back(&duration_ms);
    }
};
```

To create the new config, we create a subclass (*substruct?*) of MetaConfig, in this case called ==DevelopmentBlinkFunction==. We define a number of parameters that we will need to use within the functions logic, each with their own specific type. This is how the function/owner of this config accesses the values. Below the declaration of these parameters, we override the base class' init method to add pointers to the new parameters. 

The owner instantiates the config as one of its attributes, it calls the init function we declared previously.

Once this is done, the owner accesses the parameters within the config like the following :smile:
